### I5.8-batch-1：接通 per-model 分片配置（断点 B1）🟢 L1

**现状**：`batch_runner.py:59-62` 硬编码 `NVIDIA_MAX_SEGMENT_SEC=120` 等常量；`_segment_video:457-462` 直接用这些常量切分片。`nvidia_models.get_video_config(model_id)` 已实现返回 per-model 配置，但 `batch_runner` 不调用它。`motion_detector.py:43,72` 也硬编码 `NVIDIA_MAX_SEGMENT_SEC=120` 作为 `MotionConfig.max_segment_sec` 默认。

**根因**：v5.6.0 开发 batch_runner 时 nvidia_models 的 per-model 字段还没加，先用常量占位；后来 nvidia_models 补了字段和 `get_video_config()`，但 batch_runner 没回接。这是典型的"并行开发漏接缝"。

**方案**：在 `BatchRunner.__init__` 里按 `config.model` 调一次 `get_video_config()`，把结果存为实例属性（如 `self._video_cfg`），`_segment_video` 的 ffmpeg 命令改用 `self._video_cfg["max_segment_sec"]` 等。`MotionConfig` 的 `max_segment_sec` 也从 `self._video_cfg` 取。常量 `NVIDIA_MAX_SEGMENT_SEC/HEIGHT/FPS/MAX_FRAMES` 保留作兜底默认（不删，避免破坏其他引用——实测 `batch_runner.py:59-62` 与 `motion_detector.py:43` 都引用这些常量）。

**落地步骤**：
1. `batch_runner.py` `BatchRunner.__init__` 末尾加：调 `nvidia_models.get_video_config(self.config.model)`，存 `self._video_cfg`（dict）。
2. `_segment_video` 的 ffmpeg 命令里 `NVIDIA_TARGET_HEIGHT` → `self._video_cfg["target_height"]`，`NVIDIA_TARGET_FPS` → `self._video_cfg["target_fps"]`，`NVIDIA_MAX_FRAMES` → `self._video_cfg["max_frames"]`。
3. `MotionConfig` 构造时 `max_segment_sec=self._video_cfg["max_segment_sec"]`（替换现在的 `config.segment_sec`）。
4. `BatchConfig.segment_sec` 字段保留作"用户手动覆盖"兜底（若用户显式设非默认值则优先），默认 `None` 表"用 per-model"。
5. **注意**：`motion_detector.py:43` 的常量不要删（被 `MotionConfig.max_segment_sec` 默认值引用），只在 `BatchRunner.__init__` 传参时覆盖。

**验证标准**：
- 单测 `test_batch_runner.py` 加用例：mock `get_video_config` 返回 `{"max_segment_sec":60,...}`，断言 `_segment_video` 切出的分片 ≤60s。
- 换模型 id 为 `nvidia/cosmos3-nano-reasoner` 时，分片策略自动跟着变（不需改代码）。
- 现有 63 视频 E2E 不回归（cosmos3 与 omni 配置相同，不影响）。

**风险**：🟢 L1，per-model 字段已有默认值，未知模型回退默认配置，零回归。

### I5.8-batch-0：修复 _collect_config dict→BatchConfig 传递 bug（断点 B7）🔴 P0 优先做

**现状**：`batch_tab._collect_config:327-340` 返回 dict，`_build_runner:314-315` 直接 `_BatchRunner(config=config_dict, ...)`。`BatchRunner.__init__:154` 签名是 `config: BatchConfig`，内部用 `config.key_item_image`（属性访问）。**实测**：传 dict 立即抛 `AttributeError: 'dict' object has no attribute 'key_item_image'`。

**根因**：v5.6.0 落地时 `_collect_config` 返回 dict 供 UI 层用（测试也只断言 dict 含 key），但 `_build_runner` 没做 `BatchConfig(**dict)` 转换。`_on_start:380-385` 有 try/except 兜底，用户点"开始批量"看到的是"错误：'dict' object..."状态文案，**生产环境功能完全不可用**。37 个 `test_batch_tab` 单测全过（只断言 dict 字段，不构造 BatchRunner），是**伪实现铁则下的典型漏网**——测试绿但功能坏。

**方案**：`_build_runner` 在传 config 前做 `BatchConfig(**config_dict)` 转换。但 `BatchConfig` 当前**没有** `frame_change_pct` 字段（实测 20 个字段无此字段），而 `_collect_config` 返回的 dict 含 `frame_change_pct`——直接 `BatchConfig(**dict)` 会抛 `TypeError: unexpected keyword argument`。所以**必须先做 I5.8-batch-2 的字段添加**，或在此处 pop 掉未知字段兜底。

**落地步骤**（与 I5.8-batch-2 联动，建议合并一个 PR）：
1. `BatchConfig` 加 `frame_change_pct: int = 20` 字段（I5.8-batch-2 步骤 2）。
2. `_build_runner` 改为：`cfg = BatchConfig(**self._collect_config())`，再 `_BatchRunner(config=cfg, ...)`。
3. 或者更稳：`_collect_config` 直接返回 `BatchConfig` 实例（改返回类型），所有调用方（`_build_runner` + 测试）跟着改。
4. 加单测 `test_build_runner_constructs_batch_runner`：调 `_build_runner()` 断言返回的 `BatchRunner` 实例 `config` 属性是 `BatchConfig` 类型且 `frame_change_pct` 正确传入（覆盖当前只断言 dict 的盲区）。

**验证标准**：
- 实测：`python -c "from src.core.batch_runner import BatchRunner; BatchRunner(config={'video_dir':'D:/x','key_item_image':''},run_store=...,router=None)"` 不再抛 AttributeError。
- 新单测断言 `_build_runner()` 返回的 BatchRunner 实例 `config` 是 BatchConfig 类型。
- 真实启动应用 → 批量 tab → 填路径 → 点"开始批量" → 不再报"错误：'dict' object"。

**风险**：🔴 L3 → 修复后降为 🟢 L1。此 bug 是**生产阻断**，必须 v5.8.0 第一个修。修复本身风险低（加字段 + 一行转换），但暴露了"测试绿但功能坏"的流程问题——需补"构造 BatchRunner"的集成测试，不只断言 dict。

**关联**：此 bug 是本次反思新发现的，**未在原始记忆 [[vap-audit-record]] / [[vap-e2e-howto]] 中记录**。修复后应回写记忆。

### I5.8-batch-2：接通 UI 画面变化档位到 motion_detector（断点 B6）🟢 L1

**现状**：`batch_tab.py:76-81` 的 `_FRAME_CHANGE_OPTIONS` 5 档下拉（5%/10%/20%/30%/50%），每档带案例文案。`_collect_config:327-339` **已收** `frame_change_pct` 字段进 config dict（实测 `batch_tab.py:339`），UI 收集层**不是断点**。但 `BatchConfig`（`batch_runner.py:86-122`）**没有** `frame_change_pct`/`sensitivity_percent` 字段，`_collect_config` 返回的 dict 里这个值在构造 BatchConfig 时被丢弃；`MotionConfig`（`motion_detector.py:53-78`）仍用硬编码 `day_threshold=15/night_threshold=6`，构造时未接收 UI 值。

**根因**：UI → dict 收集通了，但 dict → BatchConfig → MotionConfig 的传递链在两处断开：(1) BatchConfig 无对应字段；(2) BatchRunner.__init__ 构造 MotionConfig 时用默认值。单位不一致（UI 百分比 0-100 vs 帧差分绝对值 0-255）也未做映射。

**方案**：定义百分比→阈值的映射函数。帧差分均值 0-255，"5% 敏感"对应低阈值（如 day=5/night=3，几乎任何变化都触发），"50% 宽松"对应高阈值（day=40/night=20，只大件物品出现才触发）。在 `BatchConfig` 加 `frame_change_pct: int = 20` 字段（**沿用 UI 已有的字段名**，不重命名为 `sensitivity_percent`），`BatchRunner.__init__` 据此算 `day_threshold/night_threshold` 传给 `MotionConfig`。

**落地步骤**：
1. `batch_runner.py` 加静态方法 `_frame_change_pct_to_thresholds(pct)`：返回 `(day, night)`，映射表：
   - 5% → (5, 3)
   - 10% → (10, 5)
   - 20% → (15, 6)（当前默认，保持兼容）
   - 30% → (25, 10)
   - 50% → (40, 20)
2. `BatchConfig` 加 `frame_change_pct: int = 20` 字段（与 `_collect_config` 返回的 dict key 同名）。
3. `BatchRunner.__init__` 构造 `MotionConfig` 时用 `self._frame_change_pct_to_thresholds(config.frame_change_pct)` 替换默认 day/night_threshold。
4. `batch_tab._collect_config` 已返回 `frame_change_pct`（无需改），但需修 **B7 dict 传递 bug**（见下）让该值真正进 BatchConfig。

**验证标准**：
- 单测：`sensitivity_percent=5` 时 `MotionConfig.day_threshold==5`；`=50` 时 `==40`。
- 真实 E2E：同一视频用 5% 档比 50% 档送 AI 片段多（更敏感）。
- UI 选档位后日志打印实际阈值，用户可核对。

**风险**：🟢 L1，默认 20% 保持现有行为，零回归。

### I5.8-agent-1：接通 batch_runner 每轮介入回调（断点 B2）🟡 L2

**现状**：`agent_orchestrator.on_task_step_done(step)` 返回 `continue/stop/switch`，但只被 `main_window._on_agent_step_done`（针对 agent 对话的工具调用）用。`batch_runner._judge_segment` 跑完一个分片**没有回调 agent**。用户场景"某视频找到人了，agent 要判断是否该停或深挖"——现在 agent 根本不知道。

**根因**：batch_runner 是 v5.6.0 落地的纯批量引擎，agent_orchestrator 是 v5.6.0 M5 落地的对话编排器，两者并行开发，"每轮介入"的接缝约定了但没接线。

**方案**：在 `BatchRunner` 加一个回调钩子 `on_segment_judged: Callable[[dict], str]`（可选，None 时不介入）。`_run_single_video` 在每个分片判断完调它，传入 `{"run_id","seg_idx","match","confidence","reason","video_name","hits_so_far"}`，返回 `"continue"/"stop"/"deep_dive"`。返回 `stop` 时设 `_cancel_flag`（只停当前视频，不整批停）；返回 `deep_dive` 时对该分片再送一次更严格的 prompt（复用 `_verify_segment` 逻辑但 prompt 更细）。

**落地步骤**：
1. `batch_runner.BatchRunner.__init__` 加参数 `on_segment_judged: Optional[Callable]=None`。

**现状**：`motion_detector._sample_frames` 串行 ffmpeg 抽帧（每帧一次 subprocess），17.7min 视频 1065 帧要 ~75s（每帧 ~70ms）。

**根因**：串行 subprocess 调用，IO 等待累计。

**方案**：用 `ThreadPoolExecutor` 并行抽帧（IO 密集，4 线程），17.7min 视频缩到 ~20s。

**落地步骤**：
1. `_sample_frames` 改用 `ThreadPoolExecutor(max_workers=4)`，每帧 submit 一个 ffmpeg 调用。
2. 持久目录下已存在的帧跳过（已有逻辑，并行也安全）。
3. 收集结果按 ts 排序。

**验证标准**：17.7min 视频抽帧 <25s（vs 现在 75s）。

**风险**：🟡 L2，并行 subprocess 需控制内存（4 个 ffmpeg 同时跑，每帧图像不大，OK）。需确保异常路径（某帧超时）不影响其他帧。

### I5.10-perf-3：run_store 查询索引优化🟢 L1

**现状**：`run_store` 有 `idx_segments_run_id/idx_clips_run_id/idx_runs_status` 索引。但 `list_runs` 按 `started_at DESC` 排序无索引。

**方案**：加 `idx_runs_started_at` 索引。

**落地步骤**：
1. `_init_db` 加 `CREATE INDEX IF NOT EXISTS idx_runs_started_at ON runs(started_at DESC)`。

**验证标准**：万级 run 时 `list_runs` 查询 <10ms。

**风险**：🟢 L1，纯加索引。

## 四、高级扩展方案（v6.x / v7.0 展望）

### 4.1 视频知识图谱（v6.1）

**第一性原理**：当前 `kb_rag` 用 CLIP embedding 做语义检索，但**时序关系**丢失（"人在 A 视频出现后 5 分钟出现在 B 视频"查不出）。

**方案**：在 `history_manager` 加"时序图谱"：每个命中是一个节点（视频名+时间戳+物品+人物特征），节点间建"时序边"（时间差 <30 分钟）+ "空间边"（同一摄像头）+ "物品边"（同一物品）。agent 查询"黑色旅行袋的移动轨迹"→ 图遍历返回时序链路。

**落地**（v6.1）：
1. 新建 `src/core/video_graph.py`：基于 `networkx` 的时序图。
2. `batch_runner` 命中时自动加节点 + 边。
3. `agent_tools` 加 `create_trace_item_tool`：图遍历返回轨迹。
4. UI 加轨迹可视化（timeline_widget 已有，扩展）。

**突破点**：从"单视频搜索"升级到"跨视频时序推理"，监控分析的核心价值。

### 4.2 多 agent 协作（v7.0）

**第一性原理**：当前 `agent_orchestrator` 是单 agent，所有意图一个 agent 处理。复杂任务（"分析 63 视频找包 + 生成报告 + 剪辑集锦"）一个 agent 上下文爆炸。

**方案**：引入多 agent 角色分工：
- **规划者（Planner）**：拆解任务，分派给执行者。
- **执行者（Executor）**：跑 batch_runner / 剪辑。
- **审查者（Critic）**：独立审查执行者结果（防误判）。
- **报告者（Reporter）**：汇总生成 MD 报告。

`agent_orchestrator` 扩展为 `MultiAgentOrchestrator`，用 LangGraph 或自研状态机驱动。参考项目 `C:\Users\Administrator.DESKTOP-EGNE9ND\Desktop\智能渗透\参考项目`（9router/Agent-Reach/AutoAgent/Archon）的 agent 协作实现。

**突破点**：从"单 agent 对话"升级到"agent 团队协作"，复杂任务能力跃升。

### 4.3 skill 自动生成（v7.0）

**第一性原理**：当前 skills 是人工蒸馏的（sparse-corridor / crowded-scene）。新场景（如"停车场车牌识别"）要人工写 skill。

**方案**：agent 遇到现有 skill 不合用的场景时，**自己写一个新 skill**：
1. agent 分析视频元数据 + 抽样几帧判断场景。
2. 选最接近的现有 skill 作为模板。
3. 调 LLM 生成新 SKILL.md（描述场景/算法/参数）。
4. 用户确认后存 `config/skills/` 下，下次自动匹配。

`skills_manager_tab` 已支持导入 skill，扩展为"agent 生成 + 用户确认 + 导入"闭环。

**突破点**：从"固定 skill 集"升级到"agent 自我进化 skill 库"。

### 4.4 分布式批量分发（v6.x）

**第一性原理**：当前 batch_runner 单机跑，63 视频要 ~15min。万级视频场景单机扛不住。

**方案**：把 batch_runner 的视频级并发扩展为多机分发：
- 主节点拆任务到 Redis 队列。
- 多个 worker 节点（可容器化）各跑几个视频。
- 结果回写共享 run_store（PostgreSQL 替换 SQLite）。

`run_store` 抽象成 Repository 接口，SQLite / PostgreSQL 双实现。

**突破点**：从"单机桌面工具"升级到"可扩展分布式分析平台"。

### 4.5 边缘部署 + RTSP 实时流（v6.x）

**现状**：`rtsp_stream.py` 已有 RTSP 接入，但是抓取式（离线分析）。[[vap-agent-capability-requirements]] 提到监控实时流。

**方案**：agent 接 RTSP 流，实时 motion_detector 检测变化 → 实时送 AI → 命中即时告警。复用 `surveillance_agent` 的两阶段搜索，但改成流式版（帧缓冲队列 + 滑动窗口）。

**突破点**：从"离线批量分析"升级到"实时监控告警"。

### 4.6 自检闭环（v7.0）

**方案**：agent 跑完批量后，自动调 `review:code-reviewer` agent 审查自己的决策日志（`decision_log`），找出"可能的误判"（如 confidence=0.6-0.7 的灰色地带），自动二次验证。形成"执行→审查→修复"闭环。

**突破点**：从"跑完即止"升级到"自检 + 修复"，结果可靠性跃升。

## 十三、完成判定标准（Definition of Done）

每个改进项满足以下全部才算完成（反伪实现铁则）：

1. **已实现**：代码已写，不是 TODO/占位/Mock（除非明确标 mock 测试）。
2. **已接通**：调用方真实调用，不是描述性占位。
3. **已跑通**：单测或 E2E 实际运行通过，有命令 + 输出证据。
4. **已验证**：真实环境验证（非 mock 的部分），或明确标注"待验证"+ 阻塞原因。
5. **已文档**：CHANGELOG.md 加条目，相关文档同步。
6. **已审查**：code-reviewer 代理过一遍，CRITICAL/HIGH 已修。

**禁止**：
- 把"理论可行""有代码片段""有界面按钮"包装成"已完成"。
- 未运行验证命令就声称"修复完成""无 bug"。
- 用 TODO/空实现/Mock 冒充生产实现。
- 为让测试变绿削弱断言、跳过测试。
