# 第零章 给执行 AI 的作业契约（先读这一章）

## 0.1 硬约束（违反即返工）

1. **不重构、不重写、不新造轮子**。本项目已经在 v9→v10.3.1 建成了 140 个 Python 模块、91 个测试文件、12 个内置 skill、32 个 Agent 工具。绝大多数需求**改现有文件即可**，禁止为了"更优雅"而重写整个文件。
2. **先接线，后新建**。本项目的最高频系统性缺陷是"**定义了但没人调用**"（详见 §1.3）。新代码之前，先 grep 是否已有实现。
3. **禁止假实现**。不准用 `...` / `pass` / `TODO` / "（略）" 代替真实逻辑。不准把 `NotImplementedError` 当作"已完成"。付费 API 一律走 `MockProvider` 并在返回值里显式标注 `mock=True`（这是本项目红线，见 `src/core/tools/media_gen/_providers.py`）。
4. **禁止未验证就宣称完成**。任何"已完成"必须附带**实际运行的命令 + 原始输出**。本项目历史上有过 CHANGELOG 过度声称导致后续会话被误导的教训（见 §1.4）。
5. **尊重既有约定**。asyncio（Agent 层）· 分层凭据（env > keyring > ini）· append-only SessionEvent · 四 waterfall 工具链 · moviepy 2.x 命名 · `REQUIRED_PACKAGES` 与 `requirements.txt` 双写同步 · 版本五同步（见 CLAUDE.md §三）。
6. **运行时数据不入库**。新建任何 `.db` / `chroma` / 日志文件前，先加 `.gitignore`。
7. **不做破坏性 Git 操作**。不 `push`、不 `reset --hard`、不 `clean -fdx`，除非用户明确要求。

## 0.2 三层交付模型（本项目的核心判据）

本项目 v10.3.0 的根本教训是：**能力建成 ≠ 用户能用**。所有批次必须按三层验收：

| 层 | 含义 | 验收方式 |
|----|------|----------|
| **L1 已建成** | 代码存在 + 单测通过 | `pytest tests/test_<area>.py -q` |
| **L2 已接线** | 生产路径真实调用（非仅测试） | `grep` 到非测试调用方 + 走通一次真实请求 |
| **L3 已送达** | **默认用户（零 env 配置）开箱可用** | 清空 `.env` 后跑 `start-desktop.bat`，功能可见可点可用 |

**任何批次如果只做到 L1/L2 就标记"完成"，视为未完成。**

## 0.3 单步 Definition of Done（DoD）模板

每一步必须同时满足：

- [ ] 改动文件 ≤ 3 个（超过则说明步骤没拆细，回退重拆）
- [ ] `python -m pyflakes <改动的 .py>` 零告警（CI 强制项）
- [ ] `python -m mypy <改动的 .py>` 无新增错误
- [ ] 新增/扩展测试文件，且**先写测试再写实现**（TDD）
- [ ] 受影响区域测试全绿（命令 + 输出留档）
- [ ] `cd webapp && npx tsc --noEmit` 0 错误（若动了前端）
- [ ] 该能力从 L1 → **L3**（默认用户路径可用）
- [ ] 若新增公开符号：有非测试调用方，或显式写 `# not-wired: <原因>`（见 P0-7）
- [ ] 回滚方式明确（env flag / 单点 revert / 数据可清空）

## 0.4 状态声明格式（每个响应开头）

```
[RIPER-5 | <Phase>.<Action> | <x/y> <unit>]
```

例：`[RIPER-5 | Execute.P0-1 | 2/4 tests passing]`

## 0.5 质量门：每次声称"完成"前必须自问

1. 默认用户（零配置、全新机器）真的能用到吗？
2. 失败路径（无 key / 无依赖 / 断网 / 磁盘满 / 超时）有用户可见的处理吗？
3. 按钮点下去有反馈吗（loading / success / error）？

# 第二章 升级总目标与设计原则

## 2.1 v11.0.0 目标定义

> **一句话**：把 TingFeng Hermes 从"**能力最全但只有专家能用**"的 v10.3.1，升级为"**小白打开就懂、点击就有反馈、AI 记得住我、技能越用越强、启动 3 秒内可用**"的 v11.0.0。

五个可量化维度：

| 维度 | v10.3.1 现状 | v11.0.0 目标 | 度量方式 |
|------|--------------|--------------|----------|
| **首屏可用** | 后端导入 29.2s | **≤ 3s**（懒加载后） | `import src.web.app` 计时 |
| **零配置可用** | 功能在但无引导 | 60 秒内完成首次任务 | 人工走查 + E2E |
| **AI 懂我** | 无画像 | 跨会话记住 ≥3 条偏好，可查看/删除 | 端到端用例 |
| **技能成长** | 蒸馏但不采纳 | 3 次同类任务 → 提案 → 采纳 → 命中 → 可回滚 | 端到端用例 |
| **交付诚实** | 4 处未接线 + 文档漂移 | 零未接线符号 + CI 自动门禁 | CI 输出 |

## 2.2 第一性原理：这个产品的本质是什么？

剥掉技术栈，TingFeng Hermes 的本质是三个动词：

1. **看**（Perceive）——把视频/流/网页/文件变成结构化事实（抽帧、YOLO、ASR、OCR、DOM 快照）。
2. **想**（Reason）——用一个可治理的 Agent 循环把事实变成结论与动作（ReAct + 工具 + 审批 + 监督）。
3. **交付**（Deliver）——把结论变成**用户拿得走的产物**（报告、pptx、短视频、字幕、上架包），且在过程中**看得懂、可中断、可回滚**。

v10.3.1 的问题不在"看"和"想"（这两层已经很强），而在**交付层的"可见性 / 可懂性 / 可带走性"**：

- 可见性缺口 → 多 agent 看不见、记忆看不见、技能看不见（B2/B3/B4/B8）。
- 可懂性缺口 → 无引导、无人话层、无反馈（B1/B7）。
- 可带走性缺口 → 无 pptx、无图像（B5/B6）。

**所以 v11 的资源分配原则是：70% 投入到"交付层"，20% 投入到"性能"，10% 投入到"新领域"。**

## 2.3 六条设计原则

| 原则 | 含义 | 反面案例（本项目真实发生过） |
|------|------|------------------------------|
| **① Deliver, not Build** | 建成 ≠ 送达。每个功能必须从 L1 走到 L3 | v10.3.0 的七个批次源码全在、默认用户全看不到 |
| **② Wire before Write** | 先接线，后新建 | `validator` / `SkillAdvisor` / `PluginLoader` 三个"已建成零调用" |
| **③ Local-first, Free-first** | 本地优先、免费优先；付费走 Mock 协议 | 已守住（`MockProvider` + `mock=True` 标注），继续守 |
| **④ Approval-before-Action** | 任何写操作/危险操作先审批 | 已建立（scope_guard 三级），继续扩展到新工具 |
| **⑤ Lazy-by-default** | 重依赖（torch/CLIP/chromadb）一律延迟到使用点 | `logic.py:32` 违反此原则，代价 19 秒 |
| **⑥ Honest-by-construction** | 文档与代码由 CI 强制一致 | CHANGELOG 曾过度声称；插件文档描述不存在的目录 |

# 第四章 P0 批次 — 交付闭环收尾与性能急救（v10.4.0）

> **目标**：消除全部"已建成零调用"缺口 + 启动性能从 29.2s 降到 ≤3s + 建立 CI 自动化门禁。

## P0-1 validator 接入 skill 准入闸门

### 根因分析（第一性原理）

`src/skills/validator.py` 实现了三重验证（跨域重叠 / 可预测性 / 排他性），但**没有任何生产代码调用它**（DIRECT：`grep -rn "skills.validator" src/` 只命中定义文件）。这意味着 `distiller.py` 蒸馏出的 skill 草稿**绕过了一切质量闸门**直接进入棘轮。

为什么会出现？因为 v10.3.0 的实现顺序是"先建独立模块 → 再接流水线"，而"接线"这一步被发布压力挤掉了。这是本项目最典型的系统性缺陷（`参考的结果计划指南.md` §"定义了但没人调用"）。

### 落地方案

1. 在 `src/skills/distiller.py` 的**候选产物生成后、写入棘轮前**插入准入调用：对每个 `SkillCandidate` 调用 `validate_skill(candidate, existing_skills, experiences)`。
2. 验证不通过时**不静默丢弃**，而是：
   - 草稿状态标记为 `rejected_by_validator`；
   - 在 `SkillCandidate` 上附加 `validation_report` 字段（含三项分数 + 失败原因）；
   - 通过 `/api/skills/distill` 的响应返回给用户（为 P1-4 的采纳 UI 供数）。
3. 用现有 `VAP_SKILLS_AUTODISTILL` 开关控制（关 = 零回归，完全跳过）。
4. **不做**：不新增 env flag，不改 validator 算法本身。

### 涉及文件

- `src/skills/distiller.py`（接入点）
- `src/skills/validator.py`（仅确认签名，不改算法）
- `tests/test_skills_distiller.py`（扩展）
- `tests/test_skills_validator.py`（确认现有断言不被破坏）

| 2 | `test_distiller_rejects_low_predictability_candidate` | 注入低可预测性经验 → 状态 `rejected_by_validator`，不写棘轮 |

## P0-6 启动性能急救（29.2s → ≤3s）★ 本批次最高价值项

### 根因分析（第一性原理 + 实测归因）

**实测数据（本机，`./venv/Scripts/python.exe`，冷进程）**：

| 测量对象 | 耗时 |
|----------|------|
| `import src.web.app`（后端入口） | **29.18 s** |
| `import src.core.logic` | 19.64 s |
| `import sentence_transformers` | **19.00 s** |
| `import torch` | 4.15 s |
| `import chromadb` | 2.37 s |
| `import scenedetect` | 1.29 s |
| `import cv2` | 0.26 s |

**归因链（DIRECT，逐层 file:line）**：

```
src/web/app.py:21  from .routers import (...)
        │
        └─► src/web/services/analyzer_service.py:14   import cv2   ← 触发 core.logic 载入
                 │
                 └─► src/core/logic.py:9   import cv2
                     src/core/logic.py:12  import torch            ← 4.15 s（急切）
                     src/core/logic.py:32  from sentence_transformers import util   ← 19.00 s（急切！）
                     （chromadb / scenedetect 随之链式载入）        ← +3.7 s
```

**根因（真正的第一性原因）**：

`src/core/logic.py:21-23` 的注释写着：

> `# Optional dependency probes — 使用 importlib 只探测不绑定，`
> `# 实际使用处（filter_frames_semantically / extract_smart_keyframes 等）再做局部 import。`

同文件对 `SCENEDETECT_AVAILABLE` / `DECORD_AVAILABLE` **确实**用了 `_probe()`（`importlib.util.find_spec`，只探测不绑定）；但紧接的第 32 行对 `sentence_transformers` **真实 import 了**：

```python
try:
    from sentence_transformers import util  # noqa: F401  (used by semantic_search / kb_indexer)
    CLIP_AVAILABLE = True
except ImportError:
    CLIP_AVAILABLE = False
```

**这一行同时违反了两条原则**：
1. 违反了同文件自己声明的"只探测不绑定"约定（C4，注释与实现自相矛盾）；
2. 违反了 lazy-by-default 原则（§2.3 原则⑤）——为了算出一个**布尔标志**，付出了 19 秒的进程启动代价。

**为什么之前没人发现**：`sentence_transformers` 只在"语义检索 / CLIP 相似度"这类**低频功能**里用，而它的代价却加在**每次进程启动**上。而启动慢又常被归因于"Electron 壳慢 / 机器慢"，问题被掩盖。

**次生影响**：
- `start-desktop.bat` 里 Electron `runtime-controller.js` 需要轮询 `/healthz` 探活，后端 29 秒才起来 → 用户看到的是**近半分钟的白屏**；
- 后端重启（崩溃断路器 re-arm，见 `desktop/crash-diagnostics.js`）会再等 29 秒；
- CI 里每个测试进程都要付这 29 秒（91 个测试文件若各自起进程，代价被放大）。

### 落地方案

**步骤 1（核心，性价比最高）**：把 `logic.py:32` 改为与同文件其他能力等价的**探测式**判断，真实 import 下沉到使用点。

- `CLIP_AVAILABLE` 改用 `_probe("sentence_transformers")`（与 `SCENEDETECT_AVAILABLE` 完全一致的写法）；
- 真实 `from sentence_transformers import util` 移到**首次使用处**（参考本仓库已有的正确范式：`src/core/agent_tools.py:166` 与 `:389` 就是**函数内局部 import**——说明本项目已接受并大量使用这一模式，**这不是重构，是回归到项目自身约定**）。

**步骤 2**：`logic.py:12` 的 `import torch` 同理做**惰性代理**。
- 但注意：`torch` 在 `check_cuda_health()`（`logic.py:44-59`）与多处张量运算中使用，不能简单删。
- 做法：模块级不 `import torch`，改为轻量 `_TorchProxy`（`__getattr__` 惰性导入）或用 `_probe("torch")` 记录可用性 + 使用点局部 import。**优先选择与项目风格一致的最小方案**：若 `torch` 使用点分散且多，用模块级惰性代理；若集中在少数函数，直接局部 import。
- **必须保留** `NVIDIA_GPU_AVAILABLE` / `CLIP_AVAILABLE` / `ADVANCED_FEATURES_AVAILABLE` 的**真实探测语义**（CLAUDE.md §三 第 8 条明确禁止把 `ADVANCED_FEATURES_AVAILABLE` 硬编码为 True）。

**步骤 3**：`chromadb`（2.37s）/ `scenedetect`（1.29s）同法下沉到使用点。

**步骤 4**：断掉 `src/web/app.py` → `analyzer_service.py:14 import cv2` 的**模块级**急切链。
- `analyzer_service.py` 只在真正跑分析时才需要 cv2 → 改为函数内 import，或使用 `TYPE_CHECKING` + 运行时惰性。
- `src/web/routers/metrics.py:57` 已经是**函数内** `import cv2`（正确范式，可作为对照）。

**步骤 5（加速启动体验，与步骤 1-4 独立）**：
- Electron 侧：`runtime-controller.js` 的探活期间显示**真实进度**（"正在加载 AI 引擎…"）而不是空白页，并设置分级超时（首帧 ≤3s 显示 splash）。
- 让 splash 先渲染，后端就绪后再 `loadURL` 主界面。

**步骤 6**：加**启动性能回归测试**（防未来回退）。

## P0-9 审批总线多会话隔离

### 根因分析

`src/web/deps.py:321-329`：

```python
_approval_bus: ApprovalBus | None = None

def get_approval_bus() -> ApprovalBus:
    global _approval_bus
    if _approval_bus is None:
        _approval_bus = ApprovalBus()
    return _approval_bus
```

**进程级单例**。`workflow_status.md` 自认："审批 SSE 队列为进程级单例（多窗口互偷事件）—— 单用户桌面场景可接受，多窗口待 P1"。

单窗口场景"可接受"，但**多窗口会串台**：A 窗口的审批弹窗可能收到 B 窗口的请求，用户点了"允许"，实际批准的却是另一个窗口的操作。**这是安全语义问题，不只是体验问题。**

### 落地方案

1. `ApprovalBus` 支持**按 session/窗口维度分区**：`get_approval_bus(session_id)` → 每个 session 一个独立 pending 队列；
2. SSE 投递时按 `session_id` 过滤，只推给对应窗口；
3. `decide(pin, allow)` 校验 pin 属于该 session，跨 session 的 pin 一律拒绝（防越权批准）；
4. 保留进程级"最近决策"ring（用于 decisions 页全局审计），但 **pending 队列按 session 隔离**；
5. Electron 侧：给每个 BrowserWindow 分配稳定 `windowId`，随 `/run_stream` 一起传。

### 涉及文件

- `src/web/deps.py`（ApprovalBus 分区）
- `src/web/routers/agent.py`（SSE 按 session 过滤 + decide 校验）
- `webapp/src/lib/api.ts`（带上 windowId）
- `tests/test_scope_guard.py` / `tests/test_agent_router_assembly.py`（扩展）
- 新增：`tests/test_approval_isolation.py`

### TDD 测试清单

| # | 测试名 | 断言 |
|---|--------|------|

## P1-3 用户画像层（双段 + 晋升规则 + 可查看/编辑/删除）

**晋升规则（借鉴 opencode-magic-context 范式）**：同一观察**出现 ≥3 次**才从 `recent` 晋升 `stable`；晋升前只在 `recent` 存在。

1. 新增 `src/core/memory/profile.py`：
   - `UserProfileStore`（SQLite，表 `profile_facts(category, key, value, confidence, hits, first_seen, last_seen, tier)`）；

   - 复用现有 SQLite 范式（与 `working.py` 一致的连接/建表写法）。
2. **注入点**（`src/core/agent/loop.py`）：在 system 段注入画像摘要，**设字符预算**（默认 ≤600 字符，env 可调），只注入 `tier=stable` + 高置信 `recent`。

4. **管理 API + 页面**：`GET/PATCH/DELETE /api/memory/profile`；webapp 新增"记忆"页（`/memory`），展示"AI 记住了我什么"，每条可编辑/删除，支持"忘掉全部"。
5. **隐私前置**：默认**本地存储、不上传**；提供总开关 `VAP_USER_PROFILE=0` 一键关闭；首次采集时给用户一次性告知。

## P1-4 skill 采纳闭环（dry-run → staged → adopt → 回滚）

### 根因分析

`src/skills/` 已有完整骨架（`distiller` / `validator` / `scoring` / `spectre` / `roster`），`/api/skills/{ratchet,distill}` 端点也在，但缺**用户可见的采纳流程**（DIRECT：无 staged/adopt 概念）。结果：蒸馏出来的技能用户看不到、不敢用、无法回滚 → 等于没做。

### 落地方案

四步流水线（照 `SkillOpt-Sleep` 范式）：

1. **dry-run（只报告）**：`POST /api/skills/distill?dry_run=1` → 只返回"如果采纳会发生什么"（新增/改进/拒绝 + 原因），**不落盘**。
2. **staged（提案预览）**：候选写入 `staged` 状态 + `config/skills_state.json` 记录，前端"待采纳"分区展示：技能名、触发场景、正文预览、安全性报告（spectre）、validator 报告（P0-1 产出）。
3. **adopt（用户采纳才落盘）**：`POST /api/skills/adopt/{id}` → 才写入 `config/skills/<name>/SKILL.md` + 更新棘轮。
4. **回滚（可撤销）**：`POST /api/skills/rollback/{id}` → 从快照恢复（采纳前先备份到 `config/skills_state.json` 的历史段）。
5. **触发质量 CI 门**：用 TF-IDF rank-1 度量"某意图是否命中预期 skill"，写成 `tests/test_skills_trigger_quality.py`，命中率低于阈值即红 → 让"技能是否真的好用"变成可测指标。

## P2-1 上下文压缩硬化（checkpoint / restore / 决定清单）

### 根因分析

1. **压缩前 checkpoint**：压缩是有损的，出问题无法回溯；
2. **压缩后 restore**：用户问"你刚才为什么忘了我说的 X"时无法恢复；
3. **决定清单**：用户看不到"哪些内容被压缩掉了"。

### 落地方案

# 第八章 扩展与超越（不被局限的进阶清单）

## 8.1 智能层算法升级

| 项 | 现状 | 升级方案 | 收益 | 成本 |
|----|------|----------|------|------|
| **语义缓存** | 无 | 对 (prompt_hash → response) 做本地向量 + 精确双查缓存（命中即返回，标注 `cache_hit`） | 重复任务零成本、响应秒回 | M |
| **混合检索升级** | experience 已 FTS5 trigram + 0.3bm25/0.4quality/0.3recency | 引入 **RRF 融合**（Reciprocal Rank Fusion）+ 可选的本地重排小模型 | 召回质量提升 | M |
| **GraphRAG** | 有三元组表但无图检索 | 用 `triples` 做 k-hop 邻域扩展，把"实体关系链"注入上下文 | 复杂问答准确率提升 | L |
| **增量索引** | 每次重建 | 按文件 mtime + hash 做增量 embedding，只更新变化片段 | 索引时间从分钟级降到秒级 | M |
| **向量量化** | 无 | ChromaDB 换用量化索引（IVF/PQ）或本地 ONNX 小模型 | 内存占用下降、检索更快 | M |
| **Prompt 版本管理** | 模板文件无版本 | 给 `config/prompts/**` 加 frontmatter 版本 + 变更记录 + 回归 eval | 提示词改动可回溯、可回滚 | S |
| **Prompt A/B** | 无 | 同一任务随机分流两个提示词版本，记录质量/成本，自动收敛到优者 | 持续自我优化 | L |
| **投机执行** | 无 | 对"高确定性下一步"提前执行（如已确定要抽帧就直接开始），命中则节省一轮 | 降低端到端延迟 | L |
| **反思循环（Reflexion）** | critic 存在但无记忆 | 把 critic 的发现写入 experience，下次同类任务前置注入 | 同类错误不再犯 | M |
| **自愈协议** | 无 | 检测"能力漂移"（同一任务成功率下降）→ 自动回退到上一个已验证的提示词/模型档 | 长期稳定性 | L |
| **工作缓冲区** | 无 | 长任务中把关键上下文写入"工作缓冲"文件，压缩/重启后可恢复 | 抗上下文丢失 | M |

# 结语：执行者必须遵守的五条铁律

1. **先测量，再优化**。本指南的 29.2s / 19.0s / 4.15s 都是实测数，不是猜测。任何优化主张都必须附实测前后对比。
2. **先写测试，再改代码**。每个批次都给了 TDD 清单——测试先红，实现后绿，最后留下"防回退"的反向断言。
3. **不许重构**。绝大多数需求是"接线"和"补 UI"，不是推倒重来。改 ≤3 个文件为一步。
4. **不许假实现**。`...` / `TODO` / "（略）" 一律禁止；付费路径一律 Mock 且标注 `mock=True`。
5. **不许未验证就宣称完成**。每条"完成"必须能贴出命令 + 真实输出；能复跑、能追溯、能回滚。

> **本指南的唯一成功判据**：一个从未用过这个产品的人，在一台干净机器上双击 `start-desktop.bat`，**30 秒内看到界面、60 秒内完成第一个任务、过程中每一步都看得懂**。
