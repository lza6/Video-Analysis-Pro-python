## Decisions and Assumptions

### 已确认事实（DIRECT）

1. 主项目三大 P0 短板：新 Agent 框架孤岛（agent.py:79）+ IM/remote 全 Mock + AES 降级（cipher.py:7-8）+ CI 门禁失效（ci.yml:42）。
2. Agent 框架代码完整（ReactLoopAgent/Session/Turn/waterfall/读写锁/subagent/插件全实现，29 测试）但"已实现未接通"。
3. v9 未 commit 未打 tag，199 项 diff 是转型收尾。
4. 8 簇报告独立收敛于若干共识（见下"跨簇强共识"）。

### 当前假设（INFERENCE）

1. 假设用户希望"先收尾 v9 再扩展"——基于三大 P0 短板影响稳定性/安全性/数据正确性，扩展新方向前应先接通。需用户确认。
2. 假设桌面单用户产品不应引入 PostgreSQL+Docker 重依赖——基于 7 簇报告均建议 SQLite 本地优先。需用户确认是否有多端同步/多租户诉求改变此假设。
3. 假设用户愿意把视频分析能力从"主功能"降为"Agent 工具集之一"——基于 CLAUDE.md v9 转型已声明。已确认。
4. 假设 ReactLoopAgent 接通 prod 后可逐步替换老 AgentOrchestrator——基于两者接口不同构（async vs sync），需适配层。待验证。

### 架构决策（基于跨簇强共识）

1. **记忆层升级走 mnemosyne BEAM 三层 + SQLite 本地优先**（mempalace+mnemosyne 双 ⭐⭐⭐ 共识），不引入 PG。
2. **skills 沉淀走 nuwa 五层蒸馏 + 棘轮机制 + 保真度评分卡**（nuwa+opencode-magic-context+skills-best-practices 三 ⭐⭐⭐ 共识）。
3. **Agent 监督层补 OpenHands stuck.py 五场景 + attempt_loop_recovery + context 压缩**（OpenHands+agent-orchestrator+pentestcode 三 ⭐⭐⭐ 共识）。
4. **Electron 壳走 DSH 四段式 + nodeterm 黑匣子日志 + OpenDesign 崩溃断路器**（DSH+Pi+holaOS+OpenDesign 四 ⭐⭐⭐ 共识）。
5. **写操作一律 staged-approval + 环境变量分级开关**（commerce-agents+claude-ads+marketing-dashboard+open-mercato 四 ⭐⭐⭐ 共识）。

### 被否决方案及原因

1. **否决：把主项目视频分析能力整体发成 MCP server 作为 v9.1 主线**——参考簇虽多项目双形态，但主项目三大 P0 短板未接通前发 MCP 是在"孤岛"上扩外延，先收尾。降为 P2。
2. **否决：引入 PostgreSQL+pgvector 做 ChromaDB 升级**——7 簇报告均坚持桌面本地优先，PG+Docker 运维负担与桌面分发冲突。坚持 SQLite+sqlite-vec/ChromaDB。
3. **否决：照搬 ECC 181 skills+47 agents 规模**——ECC 是 10+ 月沉淀结果非起点，盲目铺 skill 导致 frontmatter 误触发与维护负担。YAGNI，先 5-10 个高质量 skill。
4. **否决：迁移 Tauri 轻量化**——丢失 Node 运行时托管 Python 便利，迁移成本远大于收益。深化 Electron。
5. **否决：直接移植 open-mercato/genoffice 完整软件产品**——定位不同（ERP/Office 套件 vs Agent 桌面平台），只借鉴架构思想。
6. **否决：把 baoyu-skills 全量安装**——baoyu 自己 README 警告全量加上下文开销，应按需选。

# 第五部分：阶段五 高影响方案 Red Team（事前反证）

## Red Team P0-1：CI 门禁修复

- **未经验证假设被当事实**：假设去 `|| true` 后 v9 新测试全绿。但基线称"CHANGELOG 全绿"而 CI `|| true`，从未真验证。
- **漏了什么失败场景**：可能存在平台差异（Windows/ubuntu/macos × 3.10/3.11）导致某些组合失败；可能存在依赖缺失（ultralytics/faster-whisper 重依赖 ignore）。
- **是否过度乐观**：是，"全绿"基于 CHANGELOG 声称非 CI 实测。
- **更简单路径**：先本地 `pytest tests/ -q --ignore=test_headless_server --ignore=test_e2e_smoke` 跑标准子集确认绿，再去 `|| true`。
- **六个月后失败最可能由什么导致**：某测试在特定平台 flaky 导致 CI 红后又加回 `|| true`。
- **最小实验**：本地跑标准子集 + ruff check，确认绿再去 `|| true`。
- **最终建议**：直接实施（先本地验证绿）。

## Red Team P0-2：ReactLoopAgent 接通 prod

- **未经验证假设被当事实**：假设 ReactLoopAgent 接通后能无缝替换 AgentOrchestrator。但两者接口不同构（async vs sync），且 ProviderRouterClient 代码无定义（基线 DIRECT）。
- **漏了什么失败场景**：前端 agent 页可能依赖老 orchestrator 的同步返回行为（agent.py:31-46 同步返回意图解析+计划），切 async 后前端需改；NVIDIA 多 key 路由（_make_llm_callback）需重新桥接到 ReactLoopAgent 的 LLMClient Protocol。
- **是否过度乐观**：是，"接通"被当成简单替换，实则是接口适配+前端改造+LLM 桥接三层。
- **更简单路径**：先加 prod_adapter.py 适配层，让 ReactLoopAgent 包装成老 orchestrator 接口，灰度切换，不直接替换。
- **六个月后失败最可能由什么导致**：ReactLoopAgent 缺 ProviderRouterClient 实现，临时用 MockLLMClient 导致生产 LLM 调用失败。
- **最小实验**：先实现 ProviderRouterClient + 1 个工具接通，前端 agent 页发 1 条消息端到端验证。
- **最终建议**：先做最小实验（ProviderRouterClient + 1 工具端到端），验证后再扩大。

## Red Team P0-3：Agent 监督层

- **未经验证假设被当事实**：假设 OpenHands stuck.py 五场景直接适用 VAP。但 OpenHands 是交互式 coding agent，VAP 是视频分析+监控，卡死模式可能不同。
- **漏了什么失败场景**：监督层误判正常长任务（如长视频分析多步工具调用）为卡死，触发恢复打断。
- **是否过度乐观**：是，五场景直接照搬可能水土不服。
- **更简单路径**：先实现 1-2 个最高价值场景（同 action 同 observation 重复 + context window error 循环），feature flag 默认关，观察后再扩。
- **六个月后失败最可能由什么导致**：监督层误判导致正常任务被打断，用户关闭 feature flag 后监督层名存实亡。
- **最小实验**：1 个卡死场景 + 1 个正常长任务，验证检测准确率。
- **最终建议**：缩小范围（先 2 场景），feature flag 默认关，观察后扩。

## Red Team P0-4：cryptography 可选依赖

- **未经验证假设被当事实**：假设 cryptography 列可选依赖缺失自动降级。但当前降级 XOR 非 AES，降级模式安全性弱。
- **漏了什么失败场景**：用户生产环境无 cryptography，IM 网关用 XOR 加密，被攻击。
- **是否过度乐观**：否，降级路径已实现（cipher.py:122-161）。
- **更简单路径**：cryptography 列可选依赖 + 启动时强告警"IM 加密降级，建议安装 cryptography"。
- **六个月后失败最可能由什么导致**：用户未装 cryptography 用降级 XOR，被攻击后追责。
- **最小实验**：无 cryptography 场景测试 + 告警显示。
- **最终建议**：直接实施（降级路径已实现，加告警即可）。

## Red Team P1-1：记忆层 BEAM 三层

- **未经验证假设被当事实**：假设 mnemosyne BEAM 三层 + 混合评分能直接套用 VAP ChromaDB。但 mnemosyne 用 sqlite-vec + FTS5，VAP 用 ChromaDB，混合评分实现不同。
- **漏了什么失败场景**：ChromaDB collection 重建（MIB 二值化需重算向量）导致现有 history 数据丢失或召回率下降。
- **是否过度乐观**：是，"升级"被当成无破坏，实则需重索引。
- **更简单路径**：先加 Working Memory 热层（TTL 注入，无破坏），TripleStore + 混合评分 + MIB 二值化分批，每批可独立回滚。
- **六个月后失败最可能由什么导致**：MIB 二值化召回率下降，用户关闭记忆层退回 ChromaDB flat。
- **最小实验**：先 Working Memory 热层 + importance 权重列（无重索引），验证收益，再考虑 TripleStore + MIB。
- **最终建议**：缩小范围（先 Working Memory + importance，不重索引），验证后再扩。

## Red Team P1-3：Electron 壳四段式

- **未经验证假设被当事实**：假设 DSH 四段式直接适用 VAP。但 VAP spawn Python 子进程，DSH spawn DSH CLI，stdout 就绪信号格式不同。
- **漏了什么失败场景**：Python 后端启动慢（首次自动建前端+装依赖 serve.py:76-125），30 次探活不够。
- **是否过度乐观**：否，四段式是成熟模式。
- **更简单路径**：先加 stdout 就绪信号（serve.py 输出 "VAP ready on http://..."）+ loadURL 5 次重试，崩溃断路器 + crash reporter 分批。
- **六个月后失败最可能由什么导致**：崩溃断路器阈值过严，正常重载被阻断。
- **最小实验**：stdout 就绪信号 + 重试，验证首次启动场景。
- **最终建议**：直接实施（四段式成熟，分批落地）。

## Red Team P2-1：媒体生成工具集

- **未经验证假设被当事实**：假设 MoneyPrinterTurbo services 分层能直接借鉴。但主项目付费 API 红线，视频生成 API（如 Seedance）是付费的。
- **漏了什么失败场景**：用户无视频生成 API key，工具无法用；免费 ASR（必剪/必应）可能不稳定。
- **是否过度乐观**：是，"生成"被当成无成本，实则付费 API。
- **更简单路径**：先做免费层（VideoCaptioner 必剪 ASR + 必应翻译 + Edge TTS 免费），付费视频生成 API 走 Mock 协议验证，用户授权凭据后才真实调用。
- **六个月后失败最可能由什么导致**：用户无 API key，工具不可用，被当无用。
- **最小实验**：免费层（字幕五步）端到端，验证免费后端可用性。
- **最终建议**：缩小范围（先免费字幕层），付费生成走 Mock 协议。
